# 変異テストのゲートの見直し

状態: **決定**(2026-11-08)。所有者が §2 の方針と、§2.4 の A 案を承認しました。実装の結果は §5 にあります。§1 から §4 は、決定までの検討の記録です。

## 1. 問題

変更前のゲートは、PIT の検出率が全体で 90% 以上であることでした(`build.gradle.kts` の `mutationThreshold = 90`)。次の表は、2026-11-08 の 1 回目の実行(ゲートを変える前)の `build/reports/pitest/mutations.xml` を集計した結果です。このレポートは後の実行で上書きされたので、残っていません。構造から決まる件数(ペアヒープの 10 件、87 件、92 件、`ListConversions` の 19 件と 2 件)は、3 回目の実行のレポートでも同じでした。

| 対象 | 検出率 |
|---|---|
| 全体 | 93.50% |
| ペアヒープ(`Int`、`Long`、`Double` の値) 各クラス | 88.51%(87 件中 10 件が生存) |
| ペアヒープ(`Obj` の値) 各クラス | 89.13%(92 件中 10 件が生存) |
| `ListConversions`(`Int`、`Long`、`Char`) 各クラス | 89.47%(19 件中 2 件が生存) |
| `ListSort` 各クラス | 89.23〜93.85%(`Int`、`Char` が 89.23%) |
| `List` 各クラス | 96.07〜98.18% |
| `SubList` 各クラス | 99.28〜99.29% |

わかったことは次の 4 つです。

- **クラスごとに見ると、90% を下回るものがすでに多くあります。** ペアヒープの 18 クラスすべて、`ListConversions` の 3 クラス、`IntListSort` と `CharListSort` です。全体で基準を満たしているのは、`List` と `SubList` が平均を引き上げているからです。
- **生存変異は、すべて確認済みの等価変異です**(`docs/mutation-review.md`)。ペアヒープの 18 クラスには、どれも同じ 10 件が残っています。同じ等価変異が、生成したクラスの数だけ数えられています。
- **クラスごとに決まって残る等価変異があるので、クラスが増えるほど検出率は下がります。** 1 回目の実行の生存変異 249 件の内訳は、境界の変異(`ConditionalsBoundaryMutator`)が 133 件、`modCount++` を `modCount--` にする変異が 95 件、その他が 21 件です(3 回目の実行では 250 件で、134 件、91 件、25 件)。`modCount` の変異は、`modCount` を持つクラスすべてに入ります。これから作る `Deque`、単純ヒープ、インデックス付きヒープにも、`modCount` の変異と境界の等価変異が入る見込みです。テストの質が変わらなくても、小さなクラスが増えると全体の比率は下がります。
- **同じ変異が、型や実行によって `SURVIVED` になったり `TIMED_OUT` になったりします。** たとえば `removeAt` の境界の変異は、1 回目の実行では `Int` と `Char` の版で `SURVIVED`、`Long` と `Double` の版で `TIMED_OUT` でした。3 回目の実行では、4 型とも `SURVIVED` でした。`modCount` の変異にも同じことが起きます。そのため、検出率は同じコードでも 0.1 ポイントほど揺れます。

### 却下した案

| 案 | 却下の理由 |
|---|---|
| §7.1 の文言どおり、代表型(Int、Long、Double と各 Map)に絞る | 1 回目の実行では、Char を除いても全体で 93.13% なので、ゲートは通る。しかし、生存変異の比率は型で変わらないので、クラスが増えたときに比率が下がる問題は解決しない |
| 閾値を 85% などに下げる | すぐできるが、等価変異が多いテンプレートが増えるたびに同じ問題が起きる。根本対策にならない |
| `modCount` の値を検査するテストを足して変異を消す | 実装の細部に縛られるテストが増えるだけ(`docs/mutation-review.md` の方針)。境界の等価変異は、テストを足しても消えない |

## 2. 提案: 確認済みの生存変異との差分でゲートにする

検出率の閾値をやめます。代わりに、**確認済みリストにない未検出の変異が 1 件でも出たら失敗**にします。

§7.1 には今も「生存変異はすべて確認し、等価変異として記録するか、テストを追加」とあります。差分のゲートは、この手作業の規則を機械で検査する形にしたものです。検出率は参考値として出力しつづけます。

### 2.1 照合のキー

次の 4 つの組をキーにします。

| 要素 | 取り出し方 | 例 |
|---|---|---|
| テンプレート | 生成ファイルの 2 行目のヘッダから取る(下記) | `IntIntMaxHeap.kt` → `KTypeVTypeMinHeap.kt` |
| メソッド | `mutatedMethod` の型名を `KType`、`VType` に戻す | `mergeSortLong` → `mergeSortKType` |
| ミューテータ | `mutator` の最後の部分 | `ConditionalsBoundaryMutator` |
| 説明 | `description` の中のクラス名だけをテンプレートの名前に戻す | `removed call to ac_primitive_collections/IntSubList::checkParent` → `removed call to ac_primitive_collections/KTypeSubList::checkParent` |

- **テンプレートの名前は、生成ファイルのヘッダから取ります。** 生成ファイルの 2 行目には `// Generated from templates/KTypeVTypeMinHeap.kt.` のようにテンプレートの名前が書かれていて、`MaxHeap` の版も元のテンプレートを指しています。これを読めば、生成器と同じ対応表が得られます。生成器の規則を書き直すと二重管理になるので、そうはしません。ヘッダがないファイル(`KeySort.kt`、`Support.kt`)は、そのままの名前を使います。
- **メソッド名は正規化します。** `mergeSortInt`、`insertionSortInt`、`nextInt`、`toIntList` のように、メソッド名に型名が入るからです。
  - 対象は生成ファイルだけです。手書きのファイル(`KeySort.kt`、`Support.kt`)は、型ごとに書き分けたメソッドが別の実装なので、正規化しません。
  - 置き換えるのは、そのファイルの `KType` と `VType` の値です。値は、ファイル名とヘッダのテンプレート名を比べて得ます(`IntListMapToLong.kt` と `KTypeListMapToVType.kt` なら、`KType` が `Int`、`VType` が `Long`)。
  - 3 回目の実行のレポートでは、型名を含むメソッドは、どのファイルでも自分の `KType` のものだけです。`ListMapToVType` のファイルには変異が 1 件もありません(本体が inline で対象外のため)。
- **説明は、クラス名の部分だけを正規化します。** メソッド呼び出しを消す変異や、戻り値を置き換える変異では、説明に生成したクラスの名前が入るからです(`removed call to ac_primitive_collections/DoubleList::addAll`、`replaced int return with 0 for ac_primitive_collections/IntList::...` など)。3 回目の実行のレポートには、この種類の変異が 1157 件あります(内部クラスの名前を含むものを含む)。すべて検出されていますが、生き残ったときに型ごとに別のキーになるのを防ぎます。クラス名は、ファイル名と同じ対応表でテンプレートの名前に戻します。
- **説明の中の値の型の語(`integer`、`long`、`double` など)は正規化しません。** 多くは変異した式の型で、生成した型とは関係しないからです。たとえばヒープの `n + 1L` の変異は、どの型の版でも `Replaced long addition with subtraction` になり、`modCount++` の変異は、どの型の版でも `integer` になります。ただし、`replaced long return with 0` や `replaced double return with 0.0d` のように、`KType` の値の演算や戻り値では型の語も型で変わります。このような変異が生き残ったときは、型ごとに項目を足します(§4)。3 回目の実行の生存変異にも、型によって変わる語は 1 つもありません。
- **行番号は使いません。** 行番号を使うと、テンプレートを編集したときや、`Char` 版で行がずれたとき(`sum` がない分だけ、`openGap` は `IntList` の 741 行に対して `CharList` では 727 行)にリストが壊れます。

### 2.2 件数

同じメソッドに同じキーの変異が複数あることがあります(`siftDown` の境界の変異は 3 件)。そのため、リストの各項目には**件数の上限**を持たせます。

- 上限は、そのテンプレートから生成したどのクラスにも共通の 1 つの値です。型ごとの列は設けません。
- 型によって件数が違う場合は、最大値を上限にします。たとえば `mergeSortKType` の境界の変異は、1 回目の実行では `Int` と `Char` の版で 5 件、`Double` の版で 4 件、`Long` の版で 3 件でした。等価な変異は 5 件なので、上限は 5 件です。
- 型ごとに件数を分けない理由は、件数の違いが `SURVIVED` と `TIMED_OUT` の差によるものだからです。1 回目の実行で件数が少なかった行は、`Long` の版の 80 行と 85 行、`Double` の版の 80 行で、どれも `TIMED_OUT` でした。`KILLED` になった行はありません。3 回目の実行では、`Int`、`Long`、`Double` の版が 4 件、`Char` の版が 5 件で、`Int` の版の件数も変わりました。型で決まった差ではなく、実行ごとの揺れです。型ごとに分けると、テストの質が変わらなくても失敗することがあります。

### 2.3 判定

判定には、`mutations.xml` の各変異の `detected` 属性を使います。`status` の値の一覧(`KILLED`、`TIMED_OUT`、`MEMORY_ERROR`、`RUN_ERROR`、`NON_VIABLE`、`NO_COVERAGE` など)で判定すると、新しい状態が出たときに扱いが漏れるからです。1 回目と 3 回目の実行のレポートでは、`SURVIVED` が `detected="false"`、`KILLED`、`TIMED_OUT`、`MEMORY_ERROR` が `detected="true"` でした。

| 状況 | 結果 |
|---|---|
| 生成クラスの 1 つで、`detected="false"` の変異のキーがリストにない | **失敗**。クラス、キー、行番号、状態を出力する |
| 生成クラスの 1 つで、あるキーの `detected="false"` の件数がリストの上限を超える | **失敗**。同じく出力する |
| リストにある変異が検出された(`detected="true"`) | 成功。同じ変異でも、型や実行によって結果が揺れるため |
| リストにあるキーの変異が、どの生成クラスでも `detected="false"` にならなかった | 警告。リストが古くなっている可能性があるので、消す候補として出力する。結果が揺れるだけのこともあるので、失敗にはしない |

`NO_COVERAGE` も `detected="false"` なので、リストになければ失敗になります。これは意図した動作で、分岐カバレッジ 100% のゲートとも整合します。

照合はテンプレートの単位で行うので、同じ等価変異は 18 クラスあっても 1 件として扱われます。一方、件数の判定は生成クラスごとに行うので、1 つの型の版だけで新しく生き残った変異も検出できます。

| 案 | 長所 | 短所 |

**A を推します。** 理由のない許可を作れない形にしたいからです。表にキーの列(テンプレート、メソッド、ミューテータ、説明、件数の上限)を足し、「判定の理由」の列は今のまま残します。

### 2.5 実装の場所

- 照合の処理は `build-logic` に置き、`:build-logic:test` で単体テストします。テストの対象は、ヘッダの読み取り、メソッド名の正規化、件数の上限の判定、`detected` による判定、表の読み取りです。
- `./gradlew pitest` の後に実行されるタスクにします(仮の名前は `pitestBaseline`)。`mutationThreshold` は外すか、明らかな異常を検出するための下限(たとえば 80%)に下げます。

## 4. 残るリスク

- **等価だと誤って判断した変異は、ずっと許されつづけます。** これは変更前の方式でも同じです。リストに入れるときの確認の質に依存します。
- **inline 関数の本体は、今までどおり変異テストの対象外です**(`docs/mutation-review.md`)。差分のゲートにしても、この部分は変わりません。
- **リストにあるのと同じキーの変異が、別の理由で新しく生き残った場合は検出できません。** たとえば、テンプレートの編集で同じメソッドに同じ種類の変異が増え、その合計が上限以下に収まる場合です。件数が上限を超えれば検出できます。
- **値の型の語は正規化しないので、型によって説明が変わる変異が生き残ると、型ごとに項目が要ります。** `replaced long return with 0`、`replaced double return with 0.0d` などがこれに当たります。項目が型の数だけ増えますが、本当に違う変異を 1 つにまとめてしまうよりは安全なので、この形を選びます。
- **等価な変異の結果の揺れが、本物の生存変異を隠すことがあります。** キーに行番号を含めないので、同じメソッドにある同じ種類の変異は、同じキーで数えられます。たとえば `KTypeList` の `removeAt` の 116 行には境界の変異が 2 件あり、1 件は等価(上限 1)、もう 1 件は検出されています。テストが弱くなって後者が生き残っても、同じ実行で前者が `TIMED_OUT` になれば、件数は 1 のままでゲートは通ります。そのテストの弱さは、次に前者が `SURVIVED` になった実行で、件数が 2 になったときに検出されます。
- **件数の上限は型の最大値なので、件数が少ない型では余裕ができます。** `mergeSortKType` の境界の変異は、1 回目の実行では `Long` の版が 3 件でしたが、上限は 5 件です。そのため、`Long` の版だけで 2 件まで新しく生き残っても検出できません。揺れによる誤った失敗を避けるための、意図した妥協です。
- **キーと値が同じ型の組み合わせでは、メソッド名の値の型を `VType` に戻せません。** `IntIntMinHeap` のように `KType` と `VType` が同じ型だと、メソッド名の型名は `KType` に戻ります。そのため、ペアヒープのメソッド名に値の型の名前が入ると(テンプレートで `fooVType` と書いた場合)、`IntLongMinHeap` では `fooVType`、`IntIntMinHeap` と `LongLongMinHeap` では `fooKType` と、生成クラスによって別のキーになります。この変異を表に `fooVType` で書くと、同じ型の組み合わせの版では表にないキーになり、ゲートは失敗します。生存変異を見逃す方向ではなく、誤って失敗する方向のずれです。2026-11-08 の時点では、ペアヒープに型名を含むメソッドはないので、起きていません。起きたときは、表に `fooKType` の行を足すか、正規化の規則を見直します。

## 5. 実装の結果(2026-11-08)

- 照合の処理は `build-logic/src/main/kotlin/mutation/MutationGate.kt`、タスクは同じディレクトリの `MutationGatePlugin.kt`(プラグイン `ac.mutation-gate`)にあります。テストは `build-logic/src/test/kotlin/mutation/MutationGateTest.kt` で、`:build-logic:test` で実行します。
- `pitestBaseline` は `pitest` に依存し、`pitest` から `finalizedBy` でつながっています。`build.gradle.kts` の `mutationThreshold` は外しました。検出率は `pitestBaseline` が参考値として出力します。
- `docs/mutation-review.md` の表を、照合の列(テンプレート、メソッド、ミューテータ、説明、上限)を持つ形に書き直しました。生存変異は 26 キーにまとまり、16 行で表せます(メソッドの列に複数書ける行があるため)。
- ゲートを入れた後に `./gradlew pitest` を実行し、通過しました。この実行の結果は KILLED 3426、TIMED_OUT 149、MEMORY_ERROR 3、SURVIVED 251 で、検出率は 93.44% です。1 回目と比べて、`TIMED_OUT` が 2 件減り、`SURVIVED` が 2 件増えました。表と照合して、新しい生存変異も古くなった項目もありませんでした。見直しの修正の後の 3 回目の実行でも通過しました(検出率 93.47%)。
- 型ごとの件数の違いが実行ごとの揺れであることも、この実行で確かめられました。たとえば `LongListSort` の生存変異は、1 回目は 4 件、2 回目は 7 件でした。§2.2 で上限を型の最大値にしたのは、この揺れで失敗しないようにするためです。
- **x64 の CI でも通過しました**(2026-11-08、手動で起動した run 42483882688 の `nightly` ジョブ、コミット `b1c07a3`)。表にない生存変異も、古くなった項目の警告もありませんでした。検出は 3829 件中 3561 件で 93.00% です。変異の総数は手元(arm64)の実行と同じ 3829 件で、検出されなかった変異は、手元の 1 回目の 249 件、2 回目の 251 件に対して 268 件でした。差は表の上限の範囲に収まっています。
- **`Deque` を入れた後の表も、x64 の CI で通過しました。** PR #11 をマージした後の `ed5da43` で、手動で起動した run 42496143126(2026-11-08)と、その後の定期実行 3 回の `nightly` ジョブが成功しています。run 42496143126 の検出は 4782 件中 4474 件で 93.56% です。
- **単純ヒープ、インデックス付きヒープ、配列拡張を加えた後の表も、x64 の CI で通過しました**(2026-11-11、PR #12 のブランチで手動で起動した run 42995639080 の `nightly` ジョブ、コミット `ca6cbeb`)。表にない生存変異も、古くなった項目の警告もありませんでした。検出は 6405 件中 5924 件で 92.49% です。変異の総数は手元(arm64)の実行(`docs/mutation-review.md` の最新の実行)と同じ 6405 件で、検出されなかった変異は、手元の 474 件に対して 481 件でした。
- 表を一時的に厳しくして(`siftDown` の上限を 3 から 2 に下げ、`binarySearch` の行を消して)実行し、実際のレポートでゲートが失敗することを確かめました。出力には、生成クラス、キー、行番号、状態が出ます。ペアヒープの `siftDown` の最初の生存変異の行は、キーと値の型によって 132 行(`Int`、`Long` のキーと、`Obj` 以外の値)、133 行(`Double` のキーと、`Obj` 以外の値)、134 行(`Int`、`Long` のキーと `Obj` の値)、135 行(`Double` のキーと `Obj` の値)と異なります。行番号をキーに使わない設計にしたのは、このためです。
